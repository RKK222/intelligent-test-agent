# 工作空间文件名搜索过滤修复设计

## 背景与问题

工作空间搜索面板的产品语义是按文件名做不区分大小写的子串匹配。当前面板由应用层调用 `workspace.search`，再把服务端结果直接交给 `packages/file-explorer` 渲染。

`workspace.search` 同时被对话文件候选和需求目录定位复用。为支持按目录结构查找需求文件，服务端会匹配完整工作区相对路径。因此，当父目录包含搜索词时，该目录下文件即使文件名不包含搜索词，也会进入搜索面板结果。`filterLoadedFiles` 的本地回退逻辑同样同时匹配文件名和路径，存在一致的误报。

## 目标行为

- 搜索词去除首尾空白后，以不区分大小写的子串规则匹配文件名。
- 仅展示文件名包含搜索词的文件；父目录或其它路径片段命中不能让文件进入结果。
- 空搜索词继续展示空结果。
- 服务端搜索结果与本地已加载文件回退使用相同的文件名匹配语义。
- 文件名命中的既有高亮、打开文件和加入对话交互保持不变。

## 方案选择

在 `packages/file-explorer` 的展示边界统一执行文件名过滤：服务端结果在渲染前按 `entry.name` 过滤，本地回退的 `filterLoadedFiles` 也只按 `entry.name` 过滤。

不修改 `workspace.search` 的服务端匹配规则。该 RPC 的完整路径匹配仍供对话 `#` 文件候选和需求目录定位使用，避免为一个界面语义修复引入协议字段、后端分支和兼容处理。

不只在 `AgentWorkbench` 中过滤。文件名搜索属于 `file-explorer` 包职责，在组件边界收口可以保证其它调用方传入服务端结果时也遵守相同语义，同时覆盖没有应用层结果时的本地回退。

## 组件与数据流

1. `AgentWorkbench` 继续对搜索输入防抖，并调用现有 `api.searchFiles`。
2. `FileExplorer` 接收现有 `searchResults`、`searchKeyword` 和 `searchLoading` 属性。
3. `FileExplorer` 对有效搜索词标准化后，仅保留 `name` 包含搜索词的结果。
4. 未传入 `searchResults` 时，`filterLoadedFiles` 以相同规则过滤已加载的物理工作区文件。
5. 过滤后的结果沿用既有高亮和点击逻辑渲染；没有命中时显示“无匹配文件”。

## 测试设计

先增加会在现有实现上失败的回归测试：

- 组件测试传入两个服务端结果：一个仅父目录含“需求”，另一个文件名含“需求”。搜索面板只能渲染后者。
- `filterLoadedFiles` 单元测试构造同样的父目录误报场景，断言本地回退只返回文件名命中项。

测试预期使用手工构造的固定文件名和路径，不复用生产过滤逻辑。实现后运行 `file-explorer` 相关 Vitest、包级类型检查，并按前端规范执行受影响范围的测试与构建校验。

## 文档与兼容性

同步更新 `frontend/packages/file-explorer/README.md`，明确搜索面板最终只按文件名过滤，服务端结果也必须在包边界收口。

本次不修改 HTTP API、文件 WebSocket RPC、RunEvent、DTO、数据库或权限模型。后端路径搜索行为保持兼容；前端只移除原本不应展示的路径误报，不影响合法文件名命中结果。

## 范围与风险

修改范围限制在 `packages/file-explorer` 的搜索过滤、对应测试和包 README，不触碰当前工作区中已有的其它未提交改动。

主要风险是误把文件名大小写或首尾空白规则改得与高亮不一致。过滤与既有 `highlightKeyword` 采用相同的 `trim + toLowerCase + includes` 语义，并用大小写不敏感测试覆盖该边界。
