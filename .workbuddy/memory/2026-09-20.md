## 全量包 vs 代码变更包：现场执行命令完全一致（结论 + 复用前提陷阱）

用户问"发全包要运行啥"。核查后结论：**现场层面两包命令一模一样**，因为 `package-code-change.sh:185-248` 也是调
`package-two-backend-complete.sh` 封同一个固定名外层包 `test-agent-two-backend-complete.zip`。

现场四步（三台机器相同，见 `FULL-UPGRADE-RUNBOOK.md` §13/§14/§15）：

```bash
cd /data/0709
sha256sum -c test-agent-two-backend-complete.zip.sha256
unzip -t test-agent-two-backend-complete.zip
unzip -oq test-agent-two-backend-complete.zip
cd /data/0709/test-agent-two-backend-complete
bash deploy-backend-node.sh      # .4 / .114
bash deploy-frontend-node.sh     # .2
```

一键脚本内部行为（本次新读）：

- `deploy-backend-node.sh:7-24`：用 `detect_site_ip backend` 识别本机 IP，自动解
  `nodes/test-agent-two-backend-<IP>-SENSITIVE.tar.gz`，然后按 validate-only → 部署 → verify-only 三段跑
  `deploy-multi-backend-node.sh`，日志落 `/data/testagent/../deploy-<IP>.log`。**不需要传任何参数**。
- `deploy-frontend-node.sh`（仅 33 行）同理，读 `nodes/test-agent-two-backend-<IP>.tar.gz`（无 `-SENSITIVE` 后缀）。

**关键陷阱（本次最重要的发现）**：包内组件声明为 `reuse` 时，现场会强制校验"现网已装组件"，不满足直接失败：

- toolbox reuse → `deploy-backend-node.sh:70-83 verify_reused_toolbox()` 要求
  `/data/testagent/config/release-component-state.env` 的 `TEST_AGENT_RELEASE_TOOLBOX_FINGERPRINT`
  逐字等于包内指纹，且 `diagnose-toolbox.sh` 与 `config/toolbox.env` 存在；否则报
  `Incremental release toolbox fingerprint does not match the installed component; deploy a full component package`。
- client reuse → `deploy-internal-frontend.sh:204-217` 要求包内**不含** `dist/local-opencode-client`，
  且 manifest/签名/安装包/用户包四个 SHA 字段齐全；`:240-243` 还要在替换前端前证明现网
  `/data/apps/nginx/dist/local-opencode-client` 与发布清单逐字一致。

结论：**只有"现场已经装过且指纹未变"的节点才能吃瘦身包/代码变更包**。首次安装、灾备、换机器、
现场组件被清过 → 必须用 `--include-all-components` 的三组件全带包。

另外确认：`package-code-change.sh:163-165` 断言 worker/toolbox/client **三者都是 reuse**，
所以代码变更包永远不含组件层（这也是它只有约 150 MiB 的原因）。

## 体积对账：951 MiB 为什么不是同事说的"500 左右"（结论：不是包塞多了）

同事口径核对结果：

- **代码变更包 ≈148 MiB** ✓ 实测 `dist-code/test-agent-internal-release.zip` = 155,548,882 B = 148.3 MiB。
- **常规全量包"500 左右"** = 后端 134.4 + 前端 12.1 + 本地客户端 279.4 + 脚本 0.5 ≈ **427 MiB**。
  `MULTI-BACKEND.md:50` 记的"约 424 MiB"、`:227` 的"约 400 MiB 候选"正是这个口径（客户端 included、worker/toolbox reuse）。
- **本批 951 MiB** = 上述 427 + worker 镜像 tar 336.5 + programs 186.7 = 950.9 MiB。差额 523 MiB **全部**是 worker 运行时组件。

`package-release.sh:1787-1789` 确认 `WORKER_COMPONENT_MODE=included` 会同时拷 `test-agent-programs.tar.gz` 和
worker 镜像 tar，两者不可拆（合起来 523 MiB）。所以"带 worker 的全量包"物理上不可能压到 500 MiB。

**为什么本批必须带 worker**：`--component-plan-only` 实测（现场基线 `20260907-enterprise-deployed-components.env`）：

```
worker runtime component: included    725f3ebacf48bd913a3586994c782ac0ac429fe0efa3ccd42040d65e50e59033
toolbox component: reuse              35447da08f477dd02e458e4344be9bd870452dba12ba6db32d250c56e9f15040
local client component: included      f155b3f2a37ed24814cd58aecc530669830aa3dc3abd6f04f68a051ba6f49ebd
```

worker 现场登记 `aba0bb06…` ≠ 当前 `725f3eba…`（RTK 集成改了 worker 运行时输入）；
客户端现场 `4fabde17…` ≠ 当前 `f155b3f2…`（RTK 给客户端配置串加了 rtkLinux/rtkWindows/rtkVersion/rtkLicense，
见 `package-release.sh:977`）。**两者都必须重发，本批 951 MiB 是必要体积。**
这批部署完成后现场状态文件升到新指纹，后续全量包即可回落到 ~427 MiB。

注：上面那次 `--component-plan-only` 没带构建环境文件，所以客户端指纹是 `f155b3f2…`（`publicKey=derived`、
`publicBundleSha=missing`）。带上构建环境后的真实指纹是 `cf5c0be3…`（09-18 那次）与 `3f9108e9…`（09-20 换版本号后）。
**不带 `--env-file` 的 plan-only 只能看 worker/toolbox 判断，客户端指纹不可作为结论。**
