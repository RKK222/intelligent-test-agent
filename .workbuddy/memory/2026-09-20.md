  且 manifest/签名/安装包/用户包四个 SHA 字段齐全；`:240-243` 还要在替换前端前证明现网
  `/data/apps/nginx/dist/local-opencode-client` 与发布清单逐字一致。

结论：**只有"现场已经装过且指纹未变"的节点才能吃瘦身包/代码变更包**。首次安装、灾备、换机器、
现场组件被清过 → 必须用 `--include-all-components` 的三组件全带包。

所以代码变更包永远不含组件层（这也是它只有约 150 MiB 的原因）。

## 排查"对话改了公共 Agent 的 Skill，生效了但文件看不到"（机制梳理，非现场结论）

用户报：网页对话里更新公共 Agent 的 skill → 直接用技能确实变了 → 但看不到改动落到文件上。

代码核查结论（可复用的路径模型）：

- 用户 opencode 进程 `OPENCODE_CONFIG_DIR` 固定指向 `<sessionPath>/.testagent-runtime/current-public-config`
  **软链**（`OpencodeProcessConfigLinkService.managedConfigPath`），目标是二选一：
  - A 本人公共 worktree `{OPENCODE_PUBLIC_CONFIG_WORKTREE_ROOT}/public-{userId}/opencode`
  - B 服务器共享运行副本 `{OPENCODE_PUBLIC_CONFIG_DIR}`（默认 `{OPENCODE_PUBLIC_CONFIG_GIT_ROOT}/opencode`）
  `sessionPath` = `{OPENCODE_SESSION_DIR}/users/{统一认证号}`（企业 Linux 即
  `/data/.testagent/agent-opencode/.session/users/<认证号>`）；进程 `HOME`/`XDG_DATA_HOME`=sessionPath、
  `XDG_CACHE_HOME`=sessionPath/.cache（manager `buildStartSpec` 写死，见 `internal/process/process.go:300-306`）。
- **前端"公共级"文件树的根不是固定的**：`publicAgentRootForRead(worktreeId)` 传 worktreeId 时读 A，
  不传时读 `gitRoot`=B（`AgentConfigApplicationService:2644`）。前端 `AgentConfigPanel.vue:367` 对
  scope=PUBLIC 传的是 `publicWorktree.value?.worktreeId`。**"看不到"最常见的成因就是"写入落在 B、树在读 A"**。
- 对话里改文件是 opencode 直接写盘，**绕过平台文件 WebSocket 与角色校验**，所以平台侧无记录、无审计、
  也不进任何 Git 变更面板。
- 另有两条纯旁路落点（opencode `skill/index.ts` 的扫描根，均不在任何 Git 仓库、前端完全不可见）：
  C `<session>/.claude/skills`、`.agents/skills`、`.config/opencode/{skill,skills}`、`.opencode/{skill,skills}`；
  D `<session>/.cache/opencode/skills`（`cfg.skills.urls` 远端技能 `discovery.pull` 的缓存，per-user）。
- 技能同名优先级：`config.directories()` 顺序为 `Global.Path.config` → 工作区 `.opencode` →
  `{HOME}/.opencode` → `OPENCODE_CONFIG_DIR`，**公共配置目录最后扫描、覆盖同名**。
- 提交/发布的唯一正确通道：SUPER_ADMIN 在公共配置树里写本人 worktree → 暂存（`skills/<名>/` 一级目录
  「提交并推送」或「变更→公共Agent」）→ `POST /public/publish`/`update-and-push`：fetch+merge origin →
  投影线性提交 → push 前先建 `public_agent_config_rollouts(DRAINING)` 禁发硬闸门 → 各服务器把共享副本
  checkout/reset 到该 commit、个人 worktree `merge --no-edit` → `public_agent_config_rollout_targets`
  逐个 dispose 或（含 `.opencode/tool[s]/**/*.js|ts` 时）受管重启 → COMPLETED。
  **保存/本地 commit 都不等于发布**；共享运行副本 dirty 会在 `/public/update` 前被要求确认放弃，手工在共享副本
  commit 也会被 reset 掉。关键表：`agent_config_worktrees`（scope=PUBLIC/WORKSPACE，含 root_path/status）、
  `public_agent_config_rollouts` / `_servers` / `_targets`。

### 追加：限定"企业环境 + 超级管理员"后的收敛结论（默认就是写入 B）

`UserOpencodeProcessAssignmentService.configPath(userId)` 恒返回受管软链
`{OPENCODE_SESSION_DIR}/users/{统一认证号}/.testagent-runtime/current-public-config`，代码注释明确：
"**默认指向共享公共目录**，公共个人 worktree 保存时只切换本人链接"。软链切到 A（本人 worktree）只发生在三处：
`POST /processes/me/initialize`（仅 SUPER_ADMIN 自动准备并激活）、`POST /public/runtime-reload`
（对话页"Agent 配置更新"）、平台受管启动/重启时同服存在 ACTIVE 且稳定命名的 `public-{userId}` worktree。
→ 所以"超管在对话里改了公共 skill，生效了但文件树上看不到"的**默认解释**是：写入落在 B（共享运行副本），
而前端公共树对超管传了 `worktreeId`、在读 A。

附带两个现场事实（容易被误读为"已经发布成功"）：
- 普通用户没有公共个人 worktree（`POST /public/worktrees` 与补偿任务都要求 SUPER_ADMIN），全部回退 B →
  他们**看得见**这次改动；而超管自己（有 worktree、树读 A）看不见。
- B 是**每台 Java 各一份**的本地 clone → 其它服务器从来没有这次变化（表现为同一技能跨服务器行为不一致），
  且下一次 `/public/update`、`/public/publish` 会 reset 掉 B 的未提交改动。

最省事的决定性证据：`opencode_server_processes` 表直接存 `session_path` 和 `config_path`，
一条 join 就能拿到该用户进程的软链路径，不必先登服务器：

```sql
select p.process_id, p.linux_server_id, p.container_id, p.port, p.pid, p.status,
       p.session_path, p.config_path, p.started_at
from user_opencode_process_bindings b
join opencode_server_processes p on p.process_id = b.process_id
where b.user_id = '<user_id>' and b.agent_id = 'opencode';
```

（`agent_id` 固定 `opencode`；`config_path` 为 `.testagent-runtime/current-public-config` 说明是新受管软链模型，
需再 `readlink -f` 才知道指向 A 还是 B；直接等于公共配置目录则是升级前旧模型，直接读共享副本。）
