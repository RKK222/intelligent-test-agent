## 1. 可执行性原则

生成的 Markdown 是后续重新实现自动化的主要执行依据。它必须保存能够从当前来源还原的全部执行事实，但不得为填满模板而补造未知信息。

完整性由以下组合保证：

```text
完整请求示例
+ 所有场景差异
+ 完整 SQL
+ 完整断言
+ 必要执行状态
```

不要求为每个场景重复相同的整份报文。

## 2. 完整请求

### 2.1 完整请求示例

至少输出一个全量请求：

- 包含所有请求字段、空值字段、数组和嵌套对象；
- 静态字段使用 Excel 或代码中的具体值；
- 运行时字段使用从代码还原的可执行表达式；
- 不得使用 `${field_name}` 或 `${scenario.amount}` 等无法从输入还原的通用占位符；
- 每个字段都能在内部追溯到测试数据、代码、环境或文档，但不输出来源信息。

动态字段示例：

```json
{
  "tran_date": "${env.bex1.currentDate:yyyyMMdd}",
  "request_id": "${uuid:no-dash}",
  "amount": "101",
  "agent_no": ""
}
```

这里的动态表达式必须来自实际代码规则，不得由技能自行设计。

### 2.2 场景差异

每个场景列出相对于完整请求示例发生变化的字段及其最终值或表达式。

`i_seq_no` 只有在代码或映射证明确为 Excel 元数据时才从差异比较中忽略；如果实际进入请求，仍保留在完整请求中。

## 3. SQL

数据准备仅支持 SQL。每条已发现 SQL 必须：

- 保留完整字段、值、条件和嵌套查询；
- 标记 SQL 类型、数据库、最小执行阶段和适用场景；
- 标记执行状态；
- 保留运行时变量的实际表达式；
- 不使用省略号或伪造缺失片段。

API、SSH、Shell、文件和普通方法调用归入依赖动作，不得写成数据准备。

不评价 SQL 安全性、数据积累风险或脱敏需求。

## 4. 场景

- 场景差异和预期信息必须覆盖全部测试数据行和可达分支；
- 保留原始 TestCaseId 作为场景 ID；
- 每个场景的输入差异、运行时分支和预期结果必须在对应章节完整表达；
- 无法纳入的测试数据行进入转换报告并写明原因；
- 不得用范围或“类似场景”代替实际场景。

## 5. 断言

每条断言必须包含：

- 断言类型；
- actual 表达式；
- expected 值；
- operator 或断言方式；
- 最小执行阶段；
- 适用场景；
- 执行状态。

数据库断言表必须包含“实际 SQL”列，并直接写入完整查询 SQL、实际字段或表达式、预期值和断言方式；将 SQL 空白规范化为单行，转义 Markdown 表格分隔符，但不得删减 SQL 内容。该表不得包含“执行状态”或“来源”列。不得从测试名称、准备 SQL 或接口文档反推不存在的断言。

## 6. 缺失信息

以下内容缺少证据时统一写“未获取”，不得补造：

- 字段业务含义；
- 必输、长度、枚举和格式；
- 接口版本和超时；
- 数据库主键或表约束；
- 框架配置是否实际执行。

缺失关键请求字段或 SQL 片段导致无法重建时，将资产状态标为阻断，并在转换报告中说明，不得用占位内容冒充完整结果。

## 7. 禁止省略

正式资产不得使用以下内容代替真实信息：

- 三点省略符号；
- “同上”；
- “类似场景”；
- “其余字段”；
- `values()` 空内容；
- `${field_name}`；
- `${scenario.xxx}`；
- 未替换的 `{{templateVariable}}`。

## 8. 交付检查

- [ ] 至少一个完整请求示例包含全部字段；
- [ ] 静态值和动态表达式符合实际输入与代码规则；
- [ ] 完整请求示例与场景差异可重建全部场景；
- [ ] 全部 SQL 完整且仅 SQL 被归类为数据准备；
- [ ] 全部断言和预期值完整；
- [ ] 未知契约写“未获取”；
- [ ] 没有省略、通用占位符或模板变量；
- [ ] 正式资产和转换报告没有来源、路径、位置、指纹或证据输出；
- [ ] 转换报告记录 Excel 提取、排除项、冲突和验证结果；
- [ ] 输出校验脚本通过。
