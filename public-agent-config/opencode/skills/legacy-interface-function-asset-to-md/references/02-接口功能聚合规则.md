# 接口功能聚合规则

## 1. 主接口判断

满足越多条件，越可能是主接口：

- 位于测试方法核心路径；
- 返回值被主要断言消费；
- 方法名或 URI 与测试类/功能名称一致；
- 调用发生在准备动作之后、断言之前；
- 由被测服务注解或客户端注入获得。

造数接口、查询辅助接口、登录接口和 Mock 管理接口通常属于依赖动作。

## 2. interface_key

RPC：

```text
RPC::<service-id-or-class>::<method>::<version-or-default>
```

HTTP：

```text
HTTP::<METHOD>::<normalized-uri>
```

归一化 URI 时只替换有代码证据的运行时路径参数。

## 3. 场景集合

同一 `interface_key` 下，按测试数据行和可达代码分支生成场景。每个场景至少包含：

```text
scenario_id
scenario_name
input_variations
runtime_branch
expected_values
scenario_specific_actions
```

每条测试数据必须进入场景集合，或在转换报告中给出明确排除原因。

## 4. 公共和差异

公共区保存所有场景共享的结构与逻辑：

- 公共 SQL；
- 公共断言表达式。

场景差异和预期信息保存：

- 最终值差异；
- 动态表达式差异；
- 条件 SQL；
- Mock 返回；
- 预期值；
- 场景专属断言。

“完整请求示例 + 场景差异”必须能够重建每个场景，不需要为每个场景重复相同的整份报文。接口身份、公共生成流程和完整公共请求字段只在内部参与还原，不单独输出。

## 5. 特殊情况

- 同一方法因版本不同且行为不兼容：拆分；
- 同一 URI 但 Method 不同：拆分；
- 编排测试包含多个同等重要接口：按用户定义的功能聚合；无定义时分别输出并记录关联关系。
