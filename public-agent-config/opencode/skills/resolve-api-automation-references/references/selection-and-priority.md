# 脚本选择与来源优先级

## 脚本名结构

规范化后的 NIT `scriptId` 以两个 `##` 分成三段：

```text
第一段##第二段##第三段
```

- 第二段去空白后以 `TC` 结尾：TC 自动化脚本；
- 第二段不以 `TC` 结尾：一体化平台脚本；
- 不足三段的记录保留为内部警告，不参与后续处理。

TCDS 返回的全部脚本都与接口有关，名称不相似不是异常，不能因为相似度低而丢弃。

## 相关性排序

使用 `scripts/rank_reference_scripts.py`，以已评审案例名称、测试要点、接口 ID/英文名和用户描述作为设计文本。

排序原则：

1. 明确完整脚本名匹配；
2. 第二段名称匹配；
3. 第三段案例名与当前案例匹配；
4. 接口 ID/英文名匹配；
5. 规范化字符片段和中英文 token 重合度；
6. 分值相同时保持 TCDS 原顺序；
7. 全部候选均无正向匹配时，完整保持 TCDS 原顺序。

## TC 聚合与文件候选

TC 脚本忽略第三段案例名，按第二段 TC 名稳定聚合。第一段使用 `.` 分隔，最后一个以 `TC` 结尾的段为文件主名，之前的段为相对目录；若其后仍有其它段，不参与文件路径。例如：

```text
com.DeveloProject.到账通知处理记录查询.到账通知处理记录查询TC
```

对应候选：

```text
com/DeveloProject/到账通知处理记录查询/到账通知处理记录查询TC.java
com/DeveloProject/到账通知处理记录查询/到账通知处理记录查询TC_*.xls
```

每个文件候选同时生成以下递归逻辑路径 Glob，作为直接映射路径不完整时的兜底：

```text
**/到账通知处理记录查询TC.java
**/到账通知处理记录查询TC_*.xls
```

查找顺序和完整性要求：

1. 先在每个平台管理的自动化只读引用中尝试第一段映射出的直接逻辑路径；
2. 直接路径没有同时取得 Java 和 XLS 时，从该逻辑引用根开始递归盘点所有后代目录和文件，深度不限，分别匹配 `**/xxxTC.java` 与 `**/xxxTC_*.xls`；
3. 不能在第一个子目录、第一次部分匹配或只找到一种文件时停止。必须搜索完当前引用的全部后代，再继续其它自动化引用，直至全部引用都已穷尽；
4. Java/XLS 按 `xxxTC` 主名配对，优先使用同一逻辑父目录中的文件；Java 明确引用某个 XLS 时，以该引用关系为准，但被引用文件仍须位于平台管理的逻辑只读引用内；
5. 只有所有自动化只读引用的递归搜索均完成且仍没有完整文件组，才能判定当前候选“未找到”；不得因根目录不存在 TC 文件就提前结束；
6. 同一 TC 组可能有多个第一段候选，按排序和 TCDS 原顺序逐个尝试。当前候选穷尽后仍不完整才继续同组下一个候选，再继续下一个 TC 组。

默认最终只选择一个同时包含 Java 和至少一个 XLS 的完整 TC 组。所有搜索都使用工作区配置暴露的逻辑引用，禁止读取、构造或展示服务器物理根路径。

## 一体化平台脚本

非 TC 脚本不聚合，按当前案例关联性排序。全部无正向匹配时保持 TCDS 顺序。去重后取前 10 个作为一次一体化平台请求的 `scriptIds`。

## TC 与平台双来源

过滤后的 NIT 同时包含 TC 和一体化平台脚本时，两类候选互不替代：

- TC 排序、完整文件组查找和 Java/Excel 解析必须执行；
- 一体化平台排序、前 10 个聚合请求和返回解析也必须执行；
- 两条链路可以共享已评审案例文本，但不能因一条链路结果更相关、数据更完整或优先级更高而取消另一条；
- 来源优先级只用于同一事实的取值和冲突处理，不用于决定是否解析某个来源；
- 任一必需链路未完成时标记双来源解析不完整，不得把单来源结果包装为完整参考。

## 数据来源优先级

优先级按信息维度分别判断，不能用低优先级来源覆盖高优先级事实：

1. 当前已评审案例：案例范围、案例名称、目标异常字段、边界值、预期结果；
2. 用户上传 TC Java/Excel：报文基准值、映射、SQL、Mock、断言；
3. 只读自动化库选中的 TC Java/Excel；
4. 一体化平台中与当前案例最相关的案例；
5. 同接口成功案例：用于没有直接存量脚本的异常/边界案例基准。

`reqParamStruct` 单独作为默认请求结构权威：一体化平台返回非空结构时，最终报文字段和嵌套关系以它为基准；数组中唯一第一层节点仅作为结构根节点，实际报文不带该节点名称，直接从其 `children` 开始。普通案例全部字段不能多也不能少；已评审案例明确测试缺少某字段时，只允许且要求省略精确目标字段；明确测试新增字段时，在完整结构基础上只允许且要求加入精确目标字段；同一案例可以同时缺字段和新增字段。TC 和上传文件只提供字段值与生成方式，参考中碰巧缺少或多出字段都不能放宽结构，允许增删路径只能来自案例原文。

当某异常案例没有同名存量参考时，选择最相关成功案例作为完整基准，只修改该案例明确要求的目标字段，并同步调整该场景的数据准备和断言。其它字段、SQL 和断言保持最高优先级参考的一致值，不能删除或随意重写。

## 双来源合并而非替代

同时存在 TC 与一体化平台参考时，来源优先级只处理同一事实发生冲突的情形，不能把低优先级来源整类丢弃：

- **请求报文**：以 `reqParamStruct` 确定结构；逐字段同时检查 TC 与平台案例值、动态表达式和序列化方式。非冲突补充项合并，冲突项按优先级取值并记录内部冲突处理；
- **数据准备/恢复**：两边所有适用的非冲突动作都进入有序动作集合；完全相同的动作可以去重，但必须同时记为两边已贡献；同一目的的冲突动作按优先级处理并保留内部冲突记录；
- **断言**：合并两边非冲突的返回断言和数据库断言；完全相同断言可以去重并标记双来源；冲突预期按案例目标和来源优先级处理；
- 交叉核对或冲突处理也属于“参考”，但必须有具体字段路径、动作索引或断言路径作为内部证据，不能只写笼统说明；
- 如果某来源在某维度确有内容，该维度必须出现 `ADOPTED`、`COMPLEMENTED`、`CROSS_VALIDATED` 或 `CONFLICT_RESOLVED` 之一；不得标为未使用。
