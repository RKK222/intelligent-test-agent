# 内部结构与正式案例映射

先在 Agent 内部上下文形成 JSON 数组，每个元素遵循以下结构；该 JSON 不落盘、不直接展示：

```json
[
  {
    "case": "测试关注点描述",
    "case_id": "案例编号",
    "level1": "第一层分类",
    "level2": "第二层分类",
    "score": 1.5,
    "kws": ["关键词1", "关键词2"],
    "test_instance": {
      "test_scenario": "结合需求的测试场景描述",
      "test_steps": ["步骤1", "步骤2", "步骤3"],
      "test_data": "测试数据示例",
      "expected_result": "预期安全行为"
    }
  }
]
```

正式文件映射为四列表 Markdown：

| 正式列 | 来源 |
| --- | --- |
| 案例名称 | `case` + `test_instance.test_scenario` |
| 测试步骤 | `test_instance.test_steps`，按序号完整展开 |
| 测试数据 | `test_instance.test_data` |
| 预期结果 | `test_instance.expected_result` |

## 测试实例生成规则

为每个推荐案例生成针对性的测试实例，结合需求上下文实例化。

### test_scenario（测试场景）

将通用安全案例映射到需求的具体功能点：
- 识别需求中的具体操作对象（如"用户登录"、"文件上传"、"支付接口"）
- 将案例的通用描述转换为针对该操作的具体场景

### test_steps（测试步骤）

生成 3-5 个可执行步骤：
1. 准备测试环境/数据
2. 执行目标操作
3. 验证安全行为
4. （可选）异常路径测试
5. （可选）边界条件测试

### test_data（测试数据）

提供具体的测试数据示例：正常数据 + 异常数据（边界值、特殊字符、攻击载荷）。

### expected_result（预期结果）

描述安全机制生效时的预期行为：正面预期（应拦截/遮蔽/加密的内容）和反面预期（攻击应失败的具体表现）。
