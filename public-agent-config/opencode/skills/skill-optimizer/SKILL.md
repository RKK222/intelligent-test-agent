# 技能优化

用可复现证据改进已有技能，同时保留有效能力和兼容契约。优化必须落到技能文件与验证结果，不能只给泛化建议，也不能凭单个样例宣称整体变好。

## 职责边界

- 本技能优化已有技能；从零创建技能使用 `skill-creator`。
- 默认保持技能 `name`、目录名、公开输出契约和用户依赖路径不变。确需破坏性调整时，先说明迁移影响并取得确认。
- 不把“写得更长”视为优化。优先删除无效指令、重复资源和不能影响行为的内容。
- 不覆盖用户尚未提交的修改；先识别当前版本和基线，再编辑目标文件。

## 优化流程

### 写入边界

- 先确认平台当前打开的个人 worktree。`Working directory` 是应用输出根，普通应用目标为 `<working-directory>/.opencode/skills/<skill-name>/`；公共 Agent 编辑区若编辑根本身是 `opencode/`，目标为 `<public-config-root>/skills/<skill-name>/`。
- UI 的 `Workspace root folder`、Git 根目录、`PWD`、`OPENCODE_CONFIG_DIR`、`~/.config/opencode`、技能安装目录和共享运行副本都不能单独证明是可写目标。
- 校验时显式使用 `python3 scripts/validate_skill.py <skill-dir> --workspace-root <working-directory>` 或 `--public-config-root <public-config-root>`，两个参数互斥；不得依赖当前目录或配置变量自动推断。
- 无法证明用户归属和 worktree 身份时停止写入，保留用户未提交基线并要求先打开正确的个人工作区。

### 1. 建立基线

1. 读取目标 `SKILL.md`、它明确引用的资源、现有测试和最近反馈；
2. 记录当前版本、工作区状态、英文技术 ID、双语展示信息、输入输出契约和已知问题；
3. 保存可比较的旧版本。Git 可用时记录 commit 和 diff；否则复制到临时快照目录；
4. 把用户描述的问题转换为可观察指标，不先修改再寻找理由。

已有未提交修改时，把它们视为用户基线的一部分并保留；除非用户明确要求，不执行 reset、discard 或覆盖。

### 2. 诊断根因

实际读取 `references/quality-model.md`，逐项区分症状和根因：

- 误触发或漏触发：检查 `description` 的意图、上下文词和相邻技能边界；
- 执行不稳定：检查输入门禁、分支、停止条件、工具证据和失败处理；
- 输出不一致：检查输出契约、模板、示例与正文是否冲突；
- 上下文过长：检查是否把低频规则全部写入 `SKILL.md`，以及是否重复加载资源；
- 重复劳动：检查多次执行是否反复生成相同脚本或转换逻辑；
- 企业不可用：检查公网依赖、个人路径、未声明命令、凭据和平台耦合；
- 难以维护：检查重复规则、失效引用、超大文件和版本兼容说明。
- 展示不一致：检查技术 `name`/目录是否仍为稳定英文，`description` 是否以 `English（中文）。` 开头，以及 `metadata.display-name/display-name-zh/source` 是否齐全。

每个结论都关联具体文件、测试输出或用户反馈。没有证据时标记“待验证”，不要当成已确认根因。

### 3. 设计对照测试

在修改前建立最小但有区分度的测试集：

1. 典型成功场景；
2. 曾失败或收到负面反馈的场景；
3. 缺少输入、权限受限或工具不可用的边界场景；
4. 与相邻技能共享关键词但不应触发的近似场景。

触发问题使用 16 至 24 条真实查询，`should_trigger` 与 `should_not_trigger` 数量接近，并优先选择容易混淆的近邻任务。质量问题使用相同输入分别运行基线版和候选版；记录可获取的成功率、错误、耗时、token 或人工评分。运行环境不支持独立对照时，按相同条件串行执行并明确局限。

### 4. 按价值排序修改

按以下顺序做最小修改：

1. 修复会产生错误结果、越权操作或虚假完成的流程缺陷；
2. 保持目录和顶层 `name` 不变，补齐双语 description 和展示 metadata；保留已有 `source`，缺失时再按真实来源补齐；
3. 调整 `description` 的触发说明，提高触发召回并减少近邻误触发；
4. 补齐输入、分支、停止条件、输出和验证门禁；
5. 把低频长规则下沉到按需读取的 resources；
6. 把重复确定性操作固化为无副作用脚本；
7. 删除重复、冲突、失效或对行为没有贡献的指令。

修改要解释原因，不针对单个测试提示硬编码答案。一个问题能通过改现有段落解决时，不新建包装层或平行规则文件。

### 5. 验证候选版本

对基线版和候选版运行同一测试集与同一检查条件：

- 客观断言优先用脚本判定；
- 表达质量、业务判断和可读性保留盲审或人工评审；
- 关注平均值也关注失败样例和波动，避免均值掩盖退化；
- 如果基线和候选都轻易通过，说明断言缺少区分度，应改进测试；
- 如果质量提高但耗时或 token 显著增加，明确展示权衡。

从技能目录运行：

```bash
python3 scripts/validate_skill.py .
```

目标平台可用时再执行发现、触发和真实任务验证。没有实际运行证据时，不得声称已消除误触发、性能已提升或企业环境已兼容。

### 6. 迭代和停止

根据失败样例和用户反馈继续小步修改。满足以下任一条件时停止：

- 约定成功标准全部满足且没有已知回归；
- 新一轮没有产生有意义提升；
- 剩余问题需要业务选择、权限、外部环境或新样本；
- 优化收益不足以抵消复杂度、性能或兼容成本。

不要为了测试分数无限增加规则。保留覆盖主要风险的最小指令集。

## 交付格式

使用 `templates/optimization-report.md` 形成简洁结果，并在最终回复中包含：

1. 已确认根因及证据；
2. 修改内容和保持不变的兼容契约；
3. 基线与候选的同条件验证结果；
4. 对质量、耗时、token、安全或维护成本的权衡；
5. 未验证项、剩余风险和下一步。

若只完成诊断或结构校验，明确写“部分验证”，不能描述为优化完成。
