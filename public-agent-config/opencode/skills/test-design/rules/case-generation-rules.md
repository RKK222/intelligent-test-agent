# Phase B 测试案例组装规则

## 前置条件

Phase B 只能在以下条件全部满足时开始：

1. 当前对象已完成方法选择；
2. 每个选中方法都有 Phase A 中间物文件；
3. 中间物通过结构与证据校验；
4. 中间物状态为 `CONFIRMED` 或 `FROZEN_BY_PIPELINE`；
5. 调用输入包含完整中间物内容、文件路径和冻结/确认记录。

缺任一项时停止 Phase B，不得从需求直接补出案例。

## 非接口案例结构

```text
| 案例名称 | 测试步骤 | 测试数据 | 预期结果 |
```

默认不在四列案例表中加入案例 ID、优先级、前置条件、追溯字段。若对象规约的使用方式或最低覆盖明确要求前置条件、测试类型、优先级或备注，则按 `templates/case-template.md` 扩展为八列；设计方法、交易类型、覆盖维度和中间物映射仍只写入内部 `<task_result>`，正式案例文件不得增加设计说明或映射表。

每个选中方法分别组装到 `<业务对象名称>-<测试设计方法>-案例.md`。用户可见 skill 名使用“生成接口测试案例”“文本理解生成”；案例文件名为兼容既有产物，仍使用 `接口法 / 等价类法 / 正交法 / 路径法 / 场景法 / 规则法 / 增补法` 历史后缀。同一对象选择多个方法时生成多个案例文件，未选方法不生成文件。案例表中的案例名称仍只描述业务动作和验证点，不拼接方法名。

## 接口案例结构

接口对象使用 `test-design-api/templates/api-case-template.md` 的专用 Markdown 结构，不压缩为四列案例表；对象规约要求的附加案例字段写入模板“案例信息”区块。

## 组装规则

- 等价类：每个有效等价类至少一条正向案例，每个无效等价类至少一条反向案例；关键边界分别覆盖；
- 正交：先由已确认的因子水平表生成正交/判定组合，再按组合生成案例；
- 路径：先从已确认路径图枚举开始到结束的独立路径，再按路径生成案例；
- 场景：先从已确认场景图枚举主场景、异常、重试/补偿和终态，再按场景生成案例；
- 生成接口测试案例：按已确认接口覆盖矩阵逐项生成接口案例；
- 文本理解生成：按已确认规则与验证点表生成案例；
- 联动/增补：按已确认映射项生成或增补案例。

## 内容要求

- 案例名称使用简洁的“业务动作 + 验证点”，能唯一表达核心验证目标即可，不强制拼接测试类型、交易类型或方法名；
- 测试步骤可执行，不写“验证是否正常”；
- 测试数据必须给具体 `key=value`、边界值、组合值、报文或构造方式；
- 需要准备数据时写入步骤或测试数据；
- 预期结果写页面、接口、业务状态、数据库、消息、文件或批量结果中的可观察项；
- 只有证据明确给出表名、字段和查询条件时才写数据库断言，否则写 `需确认`；
- 一条案例可以覆盖多个中间物项，但必须在内部 `artifactToCaseMapping` 中逐项关联。
- 同一方法内部合并重复案例；不同方法的案例保留在各自文件，不跨方法合并为无方法名的汇总文件。
- 逐条落实对象规约命中规则的最低案例数量、覆盖点和必备字段；每条规则只能从其 Phase A `artifactItemRefs` 组装案例，不得在 Phase B 新增规则覆盖；互斥规则不得同时生效，材料不足以选择互斥分支时写 `需确认`。

## 禁止反推

Phase B 不得：

- 新增等价类、因子、路径、场景、接口覆盖项或规则点；
- 修改 Phase A 中间物；
- 在案例完成后反向补造中间物；
- 用案例摘要替代中间物本体；
- 将测试设计产物写入 `042-测试执行/`。
