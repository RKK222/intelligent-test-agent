# 测试设计输出路径规则

## 默认目录

默认测试设计目标为：

```text
designDocumentTarget = <I需求项>/04-测试/<S子条目>/041-测试设计/测试设计文档/
caseOutputTarget     = <I需求项>/04-测试/<S子条目>/041-测试设计/
reviewTarget         = <I需求项>/04-测试/<S子条目>/041-测试设计/<子条目名称>-案例审核结果.md
```

I/S 解析与 S 目录映射遵守 `workspace-layout.md`。无法唯一解析时不得回退到工作区根目录。

## 解析优先级

1. 用户明确指定测试设计文件路径；
2. 用户明确指定测试设计目录路径；
3. 用户未指定时分别使用 `workspaceContext.designDocumentRoot`、`workspaceContext.caseOutputRoot`；
4. 任一目标无法解析时返回 `INCOMPLETE`，不创建替代目录。

输入材料目录、右键文件目录、附件缓存目录和工作区根目录都不是隐式输出目标。未编号的 `测试设计/` 也不是默认目标。

## 目录目标下的正式文件

### Phase A 中间物

每个对象 × 方法一个文件，必须写在 `designDocumentTarget`：

```text
<业务对象名称>-<产物类型>.md
```

例如：

```text
登录页-用户名输入-等价类表.md
登录页-账号锁定-路径图.md
用户查询接口-接口覆盖矩阵.md
```

产物类型使用可直接理解的固定中文后缀：

| 方法 | 文件名后缀 |
| --- | --- |
| 等价类/边界值 | `等价类表` |
| 正交/条件组合 | `因子水平表` |
| 路径法（含状态迁移） | `路径图` |
| 端到端场景 | `场景图` |
| 接口契约 | `接口覆盖矩阵` |
| 直接规则理解 | `规则验证表` |
| 联动/增补 | `联动映射表` |

Phase A 正式文件只保存方法中间物本体，不包含对象摘要、方法选择理由、材料证据、冻结元数据或测试案例；这些内容保留在内部 `phaseAArtifactManifest`。

`041-测试设计/` 根目录、S 子条目根目录和 `042-测试执行/` 都不是 Phase A 中间产物目录。

### Phase B 案例

每个对象的每个选中方法生成一个最终案例文件，必须直接写在 `caseOutputTarget` 根目录：

```text
<业务对象名称>-<测试设计方法>-案例.md
```

用户可见 skill 名与案例文件后缀分开维护。为兼容已有产物，文件名继续使用固定历史后缀：

| 方法 skill | 用户可见名称 | 文件名中的历史方法后缀 | 示例 |
| --- | --- | --- | --- |
| `test-design-api` | `生成接口测试案例` | `接口法` | `用户查询接口-接口法-案例.md` |
| `test-design-equivalence` | `等价类法` | `等价类法` | `登录页-等价类法-案例.md` |
| `test-design-orthogonal` | `正交法` | `正交法` | `权限组合-正交法-案例.md` |
| `test-design-path` | `路径法` | `路径法` | `账号锁定-路径法-案例.md` |
| `test-design-scenario` | `场景法` | `场景法` | `批量处理-场景法-案例.md` |
| `test-design-direct` | `文本理解生成` | `规则法` | `版本兼容-规则法-案例.md` |
| `test-design-augment` | `增补法` | `增补法` | `登录联动-增补法-案例.md` |

每个案例文件只从对应方法已冻结的 Phase A 中间物组装。同一方法内部合并重复案例，多个选中方法分别保留文件，不拼成一个方法名，也不合并为无方法名的 `<业务名称>-测试案例.md`。接口法文件默认包含接口专用七区块 Markdown，其他方法文件默认包含四列案例表；对象规约的使用方式或最低覆盖指定额外字段时按规则扩展。设计说明和“中间物 → 案例”映射保留在内部 `<task_result>`。

不得把最终案例写入 `测试设计文档/`，也不生成额外索引、汇总或阶段说明文件。

### Review

阶段 3 默认直接写入 `caseOutputTarget` 根目录：

```text
<子条目名称>-案例审核结果.md
```

无法从证据得到可靠中文名称时，审核文件才回退为 `<S子条目编号>-案例审核结果.md`。

Review Agent 只写简洁案例审核结果，不修改 Phase A 或 Phase B 文件。

## 单文件目标

用户明确指定单个文件时，在同一文件中严格按以下顺序分节：

1. `测试设计文档`：Phase A 中间物本体；
2. `测试案例`：普通对象默认四列表、接口对象默认七区块 Markdown；命中规约有额外字段要求时按规则扩展；
3. `案例审核结果`：仅在同一文件目标明确包含 Review 时写入。

冻结/确认记录和中间物到案例映射只存在于内部 `<task_result>`。不得把中间物和案例混写在同一张模板表中。

## 文件名

文件名中的 `/ \\ : * ? " < > |` 替换为 `-`。

- 采用“业务名称-产物类型”，业务名称在前，用户无需打开文件即可判断内容；
- 业务名称优先使用需求或设计中的页面、接口、流程、任务、规则或数据对象名称；
- 禁止出现 `OBJ-001`、`objectId`、UUID、Phase、Stage、“中间产物”等内部或泛化词；
- 同一对象、同一方法的案例应合并为一个文件；不同方法分别使用 `<业务名称>-<测试设计方法>-案例.md`；Phase A 产物确需拆分时增加业务场景或验证点，例如 `登录页-用户名输入-等价类表.md`，不得追加 OBJ 编号；
- 连续分隔符合并为单个 `-`，去除首尾 `-`，文件名正文建议不超过 60 个字符。

## Agent 交接

- orchestrator 解析 `workspaceContext`、`designDocumentTarget`、`caseOutputTarget`、`reviewTarget`，并传材料 manifest；
- generation 在同一 Task 内先冻结事实分析基线，再写全部 Phase A 文件，最后写 Phase B 案例文件；
- manual 确认模式下，未确认前不写 Phase B 文件；
- review 只按 generation 返回的正式文件路径读取正文并写 `reviewTarget`；
- 最终结果返回 `phaseAArtifactFiles`、`caseFiles`、`resolvedDesignDocumentTarget`、`resolvedCaseOutputTarget` 和 `reviewReportFile`。
