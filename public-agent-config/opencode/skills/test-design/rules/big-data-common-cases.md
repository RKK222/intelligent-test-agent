# 大数据公共测试案例规约

## Agent 使用方式

本规约由“大数据测试指引”的“测试原则”“投产前 checklist”和“第一章 公共测试案例”整理而成，是 `test-design` 的领域附加规约，不替代 `batch-job.md`、`data-config-permission.md`、`technical-refactor.md` 等主对象规约。

仅当当前 I/S 材料出现可定位的大数据平台领域证据时读取本文件，并先确定 `domainScopes`，再评估对应规则集合：

| `domainScope` | 领域信号 | 应评估规则 |
| --- | --- | --- |
| `COMMON` | 任一 BDP、BDSP 或出湖领域已成立时自动加入 | `BIGDATA-01` |
| `BDP` | BDP、文件/高时效/实时入湖、Hudi、RA/RF，或与数据湖/入湖算法定义共现的 A/F1/F2 | `BIGDATA-02` ～ `BIGDATA-11`、`BIGDATA-21` |
| `BDSP` | BDSP、平台化作业、平台化作业组、单作业调度、应用全流程调度或对应生命周期/碎片治理 | `BIGDATA-08`、`BIGDATA-10`、`BIGDATA-12` ～ `BIGDATA-19`、`BIGDATA-21` |
| `OUTBOUND` | 出湖，或明确的“湖表 → bin/chk 等文件 → 传输任务 → 下游接收”链路 | `BIGDATA-20` |

`SEAS` 同时可能服务于 BDP 和 BDSP，不能单独决定领域；必须结合入湖表/加载算法、平台化作业/作业组等上下文选择。A/F1/F2、RA/RF 等短标识只有满足表中 BDP 上下文时才算信号；孤立字母、普通“批量”“CSV”“文件”“数据加工”和没有湖表导出语义的 bin/chk 均不加载本文件。

加载后，`objectRuleBindings` 必须按“同一 `objectId` + `big-data-common-cases.md`”单独登记，使用 `bindingType=DOMAIN_EXTENSION`，在 `domainScopes` 中写入实际命中的领域，在 `expectedRuleIds` 中写入各领域规则集合去重后的并集，并在 `loadEvidence` 中保存每个领域的材料锚点；不得为 BDP 对象评估 BDSP 专属规则，也不得反向混用。若同一材料同时涉及 BDP 和 BDSP，应优先按独立职责拆成对象并用 `objectRelations` 关联；确属不可拆分的端到端对象时，才在同一绑定登记多个领域。同一对象仍须以 `bindingType=PRIMARY` 另行登记主对象规约。命中项必须逐条绑定材料证据、最低覆盖、Phase A 中间物项和 Phase B 案例引用。

普通案例继续使用 `test-design` 的四列格式。原文中的“BDP 测试、BDSP 作业、出湖”和“静态验证、功能验证”用于规则路由与案例命名，不额外扩展正式案例字段。表名、目录、菜单名、算法名和平台名均为候选核对位置；当前材料未确认时写“需确认”，不得把本规约中的示例当成项目事实。

原文中的首存文件性能、入湖性能和 BDSP 作业性能条目属于现有暂缓性能规约，本文件不为它们分配启用编号，也不在当前功能案例设计中生成。以后明确启用性能设计时，再按 `non-functional-performance.md` 的接入规则处理。

## 通用基线

### BIGDATA-01 生产等价数据与真实链路

- 适用域：`COMMON`。
- 触发条件：本领域附加规约已按材料证据加载。
- 必须分析：先区分运行型对象和纯静态对象。在数据治理、保密、测试环境准入和技术条件均允许时，运行型对象优先使用合法授权的生产数据；任一条件不允许或技术上不可用时，按生产分布、量级和运行状态准备生产等价数据。运行型对象必须建立四组数据维度矩阵：验证日期覆盖工作日、节假日、年末、月末、季末、跨年、跨月且连续至少 2 日；交易类型覆盖新增、修改、删除三类；交易量覆盖当天有交易、当天无交易；数据质量覆盖正常数据、生僻字（如𠮷、㐭、𪚥等 Unicode 扩展字符）、换行符（`\n` / `0x0A`）、回车符（`\r` / `0x0D`）、特殊字符（如 `<>"/\|*?#&%$!@`、Emoji、零宽字符等）、字段首尾隐藏占位符。后续步骤必须消费前序步骤真实产物，不能短路链路或用手工结果冒充上游输出。纯静态对象只核对设计、登记、带出配置和实际文件/脚本，不虚构运行链路或生产数据。
- 最低覆盖：运行型对象的上述四组测试要点必须逐项生成对应案例，不得仅作为分析项，也不得因需求文档未提及而省略；可合并相容维度（如同一案例同时覆盖“工作日+新增+有交易+生僻字”），但每个维度至少有一条独立案例证明其被覆盖，且不能遗漏覆盖点，并至少包含一条从真实上游产物到下游结果的完整链路，核对记录数、内容、码制、字段对齐、隐藏占位符、日志和下游处理结果。各覆盖点先绑定 Phase A 中间物，再组装 Phase B 案例；材料未明确的字段、码值和业务预期仍写“需确认”，不得为补齐案例自行推断。纯静态对象至少形成“设计值 → 登记/配置值 → 实际带出文件或脚本值”的可定位核对证据，运行链路最低覆盖记为 `NOT_APPLICABLE`。
- 排除条件：没有大数据平台领域证据时不加载本文件；纯静态对象的运行数据矩阵和端到端链路记为 `NOT_APPLICABLE`。
- 来源定位：`测试原则`；`第一章 公共测试案例` 中各入湖、BDSP 作业和出湖案例的数据准备要求；测试人员对话明细中将四组测试要点改为必须生成案例的明确要求，以及对话中成功写入并回读的字符示例和最低覆盖要求。

## BDP 入湖

### BIGDATA-02 BDP 静态登记、设计与带出信息一致性

- 适用域：`BDP`。
- 触发条件：材料涉及 BDP 文件入湖、高时效入湖、实时入湖或对应登记、带出配置。
- 必须分析：核对源表、湖表结构与 SEAS 登记及实际带出结构一致；核对文件入湖表名、作业名、加载算法、定长/非定长、分隔符、换行符、文件类型和下载路径；核对作业及其执行脚本存在且内容正确；核对批量作业、文件传输已经登记。详细设计至少应给出作业组、作业、表、实现逻辑和前后依赖；配合测试材料还应覆盖实际涉及的菜单、联机服务、文件接口、批量任务及技术、业务验证点。
- 最低覆盖：对当前对象实际涉及的表结构、入湖源配置、加载路径、作业、脚本、SEAS 登记和详细设计逐项核对，至少各形成一个验证点；配置值与设计或实现不一致时给出可定位差异。
- 排除条件：未涉及的登记表、文件属性或作业脚本不适用；`BDP_TABLE_STRUC`、`BDP_TABLE_SRC`、`BDP_LOADJOB_FILELIST_REL`、`ETL_JOB`、`ETL_JOB_SCRIPT` 仅是候选核对位置，材料未确认时写“需确认”。
- 来源定位：`BDP 测试/静态验证/表结构静态测试`；`带出信息静态测试`；`软需登记检查`。

### BIGDATA-03 BDP 首存文件批量调度

- 适用域：`BDP`。
- 触发条件：材料涉及首存文件生成、分发和首次批量入湖。
- 必须分析：按生产首存数据分布和历史跨度准备数据；实际历史超过 100 天时必须包含超过 100 天的数据。覆盖 `BIGDATA-01` 的适用日期、交易类型、交易量和字符维度；沿真实链路生成首存文件、完成传输并由 BDP 加载。
- 最低覆盖：至少一条完整的“上游批量生成首存文件 → 文件分发 → BDP 加载”案例；核对源文件与入湖表记录数和字段值一致、无乱码错位和隐藏占位符，加载日志无异常。历史跨度要求存在时覆盖大于 100 天边界。
- 排除条件：不是首存或首次全量加载时不适用；DBF、UDS 等产品名只有材料确认后才能写入正式步骤。
- 来源定位：`BDP 测试/首存测试/首存文件批量调度`。

### BIGDATA-04 BDP A 与 F1 文件入湖

- 适用域：`BDP`。
- 触发条件：材料明确使用 A 增量算法和 F1 全量替换算法进行文件入湖。
- 必须分析：先确认 F1 作业对 A 作业的依赖和执行顺序；至少连续两个业务日准备 `BIGDATA-01` 适用数据。核对 A 表当日 `pt_dt` 分区与当日增量文件一致；核对 F1 表当日 `pt_dt` 分区是截至 T 日的完整全量结果，而不是与前一日重复累加。
- 最低覆盖：A 增量加载和 F1 全量替换各至少一条，覆盖连续两日、有数据/无数据以及适用的新增、修改、删除；逐项核对记录数、字段内容、码制、字段对齐、隐藏占位符和加载日志。
- 排除条件：F1 与 F2、RF 等全量算法按当前对象实际算法选择；算法或分区口径未确认时记为 `MISSING_EVIDENCE`，不得同时套用冲突预期。
- 来源定位：`BDP 测试/功能验证/文件入湖测试` 中 A 与 F1 算法案例。

### BIGDATA-05 BDP A 与 F2 文件入湖

- 适用域：`BDP`。
- 触发条件：材料明确使用 A 增量算法和 F2 全量合并算法进行文件入湖。
- 必须分析：先确认 F2 作业对 A 作业的依赖和执行顺序；至少连续两个业务日准备 `BIGDATA-01` 适用数据。核对 A 表当日 `pt_dt` 分区与当日增量文件一致；核对 F2 表当日 `pt_dt` 分区由 T-1 日全量与 T 日增量按材料规则合并得到。
- 最低覆盖：A 增量加载和 F2 跨日合并各至少一条，覆盖连续两日、有数据/无数据以及适用的新增、修改、删除；同时核对合并后的记录数、字段内容、码制、字段对齐、隐藏占位符和加载日志。
- 排除条件：F2 与 F1、RF 等全量算法按当前对象实际算法选择；合并主键、冲突覆盖顺序或删除语义缺失时写“需确认”。
- 来源定位：`BDP 测试/功能验证/文件入湖测试` 中 A 与 F2 算法案例。

### BIGDATA-06 BDP 高时效入湖批次与日终结果

- 适用域：`BDP`。
- 触发条件：材料涉及高时效入湖的单批次、多批次或日终汇总。
- 必须分析：分别识别单批次和多批次是否适用；确认 F 类作业对 A 类作业的依赖；按真实批次顺序加载 bin 文件，核对每批增量和日终全量结果。多批次时必须验证批次间不重不漏、顺序正确且日终结果包含全部适用批次。
- 最低覆盖：实际支持的单批次、多批次形态各至少一条；连续至少两日，并覆盖 `BIGDATA-01` 的适用维度。核对 A 增量分区与 bin 文件一致、F 类分区为 T 日正确全量、数据质量和日志正常。
- 排除条件：材料只支持一种批次形态时另一种不适用；F 类算法和合并语义未说明时写“需确认”。
- 来源定位：`BDP 测试/功能验证/高时效入湖` 中单批次和多批次日终入湖。

### BIGDATA-07 BDP Hudi 注册、实时消费、删除与日终入湖

- 适用域：`BDP`。
- 触发条件：材料涉及 Hudi 实时入湖、RA/RF 算法，或 Hudi 表结构、视图、移行、修数、注册和启动发生新增或变更。
- 必须分析：先确认 RA、RF、A、D、F 及分区名称的实际映射。完整核对表结构、视图、权限、注册和启动状态；再以实际消息或文件驱动数据消费，核对 A 类增量、D 类删除和 F 类 `latest` 最新全量，F 类结果按材料确认的规则由 T-1 全量与当日新增、修改、删除合并得到，只有材料明确时才使用 bin；最后执行日终作业，核对 RA 的 T 日有效增量以及 RF/F 类 T 日 `pt_dt` 由 T-1 全量、T 日增量和 T 日删除按材料规则合并。表结构/视图变更、移行或修数涉及 Hudi 时，同样必须覆盖注册、启动、数据消费和日终作业，不能只停在静态或启动状态。
- 最低覆盖：至少一条“注册/启动 → 实时消费 → 日终作业”完整链路；连续至少两日，覆盖新增、修改、删除、有交易和无交易，并核对源消息/文件、RA/A、D、RF/F 之间的记录数和字段级一致性、码制、字段对齐、隐藏占位符、状态和日志。
- 排除条件：当前对象不是 Hudi 或 RA/RF 实时入湖时不适用；只有“Hudi”名称但缺少本次表、算法或链路信息，或者环境暂时无法执行消费/日终时，记为 `MISSING_EVIDENCE` 并提出确认点，不得把消费或日终直接排除。RA、RF、A、D、F、bin、`latest`、`pt_dt` 等名称和合并口径必须由当前材料确认。
- 来源定位：`BDP 测试/功能验证/HUDI 实时入湖` 中 RA/RF 和日终测试。

### BIGDATA-08 BDP/BDSP 表结构、视图和文件接口变更影响

- 适用域：`BDP`、`BDSP`。
- 触发条件：BDP 入湖或 BDSP 作业修改、删除表结构、视图或文件接口。
- 必须分析：先按领域分别识别直接和间接上下游。BDP 分支核对结构带出、迁移脚本、视图重建、表/视图权限、文件契约和传输任务；涉及 Hudi 时继续按 `BIGDATA-07` 验证注册、启动、数据消费和日终作业。BDSP 分支核对表/视图重新赋权，并通过全量代码或依赖关系查询定位全部受影响作业及作业组。两个分支都必须把受影响链路纳入动态验证和联测，不得用一个领域的结果代替另一个领域。
- 最低覆盖：每个实际命中的领域分别覆盖静态结构、权限、直接依赖、间接依赖和动态调度；BDP 文件接口变更还要覆盖契约和传输，BDSP 表/视图变更还要覆盖全部查询到的依赖作业。删除场景必须证明已删除对象不再被错误引用，保留链路仍可正常处理。
- 排除条件：只新增且没有既有上下游影响的对象可跳过删除分支，但仍须核对新增依赖；依赖查询工具和权限恢复方式未确认时写“需确认”。
- 来源定位：`文件接口有变动或者删除`；`表结构、视图有变动或者删除`；`BDSP 作业/表结构或视图修改、删除验证`。

### BIGDATA-09 BDP 移行与修数

- 适用域：`BDP`。
- 触发条件：材料涉及数据移行、历史补数或修数。
- 必须分析：按生产数据分布和历史跨度准备数据，实际跨度超过 100 天时覆盖超过 100 天；通过当前材料指定的真实流水线执行迁移或修数代码，再核对数据结果。涉及 Hudi 时继续验证视图、权限、注册、启动、消费和日终作业。
- 最低覆盖：至少一条完整的“流水线执行代码 → 移行/修数 → 数据核对 → 后续处理周期”案例；核对迁移前后记录数、关键字段、码制、字段对齐和隐藏占位符。存在超过 100 天历史时覆盖该边界。
- 排除条件：不涉及历史数据变化时不适用；流水线、迁移范围、对账口径或修数覆盖策略缺失时记为 `MISSING_EVIDENCE`，不得用未获材料确认的手工改数替代。
- 来源定位：`BDP 测试/功能验证/移行或修数测试`。

### BIGDATA-10 BDP/BDSP 跳批与中断后续作

- 适用域：`BDP`、`BDSP`。
- 触发条件：投产或生产中断后需要按手册执行跳批，或材料定义跳过异常业务日期后续作。
- 必须分析：按当前对象所属领域构造与生产一致的中断位置和业务日期，使用对应 BDP 或 BDSP 跳批手册执行；核对跳批状态、业务日期、未处理数据保护、后续依赖作业启动顺序和最终数据结果。一个领域的跳批结果不能替代另一个领域。
- 最低覆盖：每个实际命中的领域至少一条“中断 → 跳批 → 后续依赖完成”完整案例；连续业务日场景下核对前后日数据隔离和衔接。
- 排除条件：系统不支持跳批且无对应恢复要求时不适用；跳批手册、允许条件或数据处置口径缺失时记为 `MISSING_EVIDENCE`。
- 来源定位：`BDP 测试/跳批验证`；`BDSP 作业/跳批验证`；`测试原则` 中生产等价运行状态要求。

### BIGDATA-11 BDP 上下游联测

- 适用域：`BDP`。
- 触发条件：当期功能、表、视图、文件接口、作业或依赖关系发生变化并影响上下游应用。
- 必须分析：明确变更点、上游输入、下游消费者、联测责任边界和可观察结果；使用真实前序结果驱动后续链路；覆盖直接依赖和材料确认的间接依赖。
- 最低覆盖：每条受影响链路至少一条端到端联测；核对接口或文件交互、落表结果、作业状态和下游业务结果，不能只证明本作业单独成功。
- 排除条件：有证据证明对象完全无上下游依赖时不适用；影响范围未完成时记为 `MISSING_EVIDENCE`，不得用“联测正常”概述代替清单。
- 来源定位：`文件接口有变动或者删除`；`表结构、视图有变动或者删除`；`上下游联测`。

## BDSP 作业

### BIGDATA-12 BDSP 生命周期配置与静态检查

- 适用域：`BDSP`。
- 触发条件：材料涉及 BDSP 平台化作业、作业组或其生命周期、SEAS、脚本和依赖配置。
- 必须分析：核对每个作业组的数据生命周期配置和清理配置；核对 SEAS 表结构、文件传输任务、作业依赖和带出排程文件；执行平台化作业静态校验的全部适用项；核对目标环境实际部署脚本与当前交付版本一致。生命周期目录和命名规则按当前材料确认。
- 最低覆盖：生命周期、表结构登记、文件传输、作业依赖、带出排程文件、作业组静态校验和部署脚本逐项覆盖当前对象实际涉及的部分；每项都给出配置值、设计值和实际值的核对结果。
- 排除条件：本卡只核对生命周期/清理配置的静态正确性，不替代 `BIGDATA-16` 的真实清理执行；未涉及的 SEAS 或文件传输子项不适用；`$WORK_ROOT/pgm/clr/`、`${BDSP_ROOT}` 等路径只是候选结构，材料未确认时写“需确认”。
- 来源定位：`BDSP 作业/静态检查` 中数据生命周期、SEAS 登记、作业组静态检查和 HQL 脚本验证。

### BIGDATA-13 BDSP 作业新增、修改、删除与依赖

- 适用域：`BDSP`。
- 触发条件：BDSP 作业或作业组发生新增、修改、删除，或前后依赖发生变化。
- 必须分析：静态核对带出脚本、当前作业依赖和依赖当前作业的其他作业组；检查依赖脚本中的作业组名无首尾空格等隐藏字符；动态调度变更对象及受影响依赖。删除时还要证明删除信息已从脚本和依赖关系中移除，剩余作业组继续正常运行。
- 最低覆盖：新增/修改按实际变更至少一条，删除按实际变更至少一条；每类都同时覆盖静态依赖检查和动态调度结果，并核对处理数据。
- 排除条件：只评估当前实际发生的变更类型；未提供完整依赖图时记为 `MISSING_EVIDENCE`。
- 来源定位：`BDSP 作业/功能验证/新增、修改作业及作业验证`；`删除作业或作业组验证`。

### BIGDATA-14 BDSP 单作业调度（原文：作业单调）

- 适用域：`BDSP`。
- 触发条件：材料要求对新增、修改或存量 BDSP 作业执行单作业调度。
- 必须分析：按日、月、年等实际频率应用 `BIGDATA-01` 的日期、数据量和字符维度；从平台单作业调度入口发起作业并通过运维查询核对运行状态；验证落表和下游依赖结果。
- 最低覆盖：每种实际调度频率至少一条，覆盖有数据和无数据；日期边界逐项覆盖但不要求机械笛卡尔积。核对调度终态、记录数、中文码制、字段对齐、隐藏占位符和下游处理。
- 排除条件：当前对象不是 BDSP 作业或不支持单作业调度时不适用；平台菜单名和查询入口未确认时写“需确认”。
- 来源定位：`BDSP 作业/功能验证/BDSP 作业单调`。

### BIGDATA-15 BDSP 作业组全流程外部触发

- 适用域：`BDSP`。
- 触发条件：材料要求执行 BDSP 作业组全流程调度，特别是验证 BDP 变更后的依赖链路或外部系统触发。
- 必须分析：按实际频率和 `BIGDATA-01` 数据矩阵准备数据；在投产前通过真实全流程调度入口执行，材料支持时选择外部系统触发；观察整组作业和跨平台依赖的启动顺序、终态及数据流转。
- 最低覆盖：至少一条从外部或真实上游触发到全部下游依赖完成的全流程案例；核对落表记录数、码制、字段对齐、隐藏占位符和下游处理结果。
- 排除条件：没有作业组或外部触发能力时跳过对应子项；触发方式和全流程范围不明确时写“需确认”。
- 来源定位：`BDSP 作业/功能验证/作业组全流程调度（外部系统触发）`。

### BIGDATA-16 BDSP 数据清理

- 适用域：`BDSP`。
- 触发条件：BDSP 作业组包含按日、月、年或其他周期的数据清理。
- 必须分析：按实际周期连续准备多个清理周期的数据；分别识别应清理、边界保留和业务仍在使用的数据；执行真实清理作业并核对清理范围、数量、索引或分区状态及后续作业。
- 最低覆盖：连续多个周期、周期边界、应清理和应保留各至少一个检查点；清理后继续执行一个依赖处理周期，证明无误删和次生中断。
- 排除条件：无清理能力时不适用；保留期限和清理边界缺少材料证据时写“需确认”。
- 来源定位：`BDSP 作业/功能验证/数据清理验证`。

### BIGDATA-17 BDSP 一次性作业退出

- 适用域：`BDSP`。
- 触发条件：应用存在只允许运行一次、完成后需要退出或删除的一次性作业。
- 必须分析：先验证一次性作业功能和数据结果；完成后按正式流程退出或删除；再次执行所在作业组及依赖作业组，确认不再引用该作业且链路正常。
- 最低覆盖：一次性作业成功执行、退出/删除、所在作业组续跑和依赖作业组续跑各至少一个检查点。
- 排除条件：周期性或长期保留作业不适用；退出时机和删除方式未明确时写“需确认”。
- 来源定位：`BDSP 作业/功能验证/一次性作业验证`。

### BIGDATA-18 BDSP 碎片治理

- 适用域：`BDSP`。
- 触发条件：材料涉及表碎片合并、碎片治理作业或对应作业组。
- 必须分析：按实际频率和 `BIGDATA-01` 的适用日期、交易类型、数据量和字符维度准备数据；执行碎片治理作业及作业组；核对治理前后数据、分区或文件状态以及依赖作业结果。
- 最低覆盖：至少一条完整碎片治理调度；覆盖连续至少两个适用周期，并证明记录数和业务数据不丢不重、作业组及依赖链路正常。
- 排除条件：材料无碎片治理能力时不适用；治理阈值、对象范围或验收指标缺失时写“需确认”。
- 来源定位：`BDSP 作业/功能验证/碎片治理`。

### BIGDATA-19 BDSP 交付与投产流水线

- 适用域：`BDSP`。
- 触发条件：当期 BDSP 改造需要通过交付、回装或投产流水线部署。
- 必须分析：投产前在材料指定的回装或等价环境执行真实流水线；核对带出的表、视图、作业、脚本、依赖和权限与变更范围一致；检查部署日志，并在部署后执行当期改造的代表性功能链路。
- 最低覆盖：至少一条流水线部署和一条部署后功能验证；部署日志无未解释异常，实际带出清单与改造清单一致，权限和运行结果正确。
- 排除条件：当前工作单元没有交付或部署变化时不适用；环境、流水线和带出范围未提供时记为 `MISSING_EVIDENCE`。
- 来源定位：`BDSP 作业/功能验证/流水线验证`；公共案例前的投产检查原则。

## 出湖

### BIGDATA-20 出湖文件、传输与变更影响

- 适用域：`OUTBOUND`。
- 触发条件：材料涉及从湖表生成 bin/chk 等文件并通过传输任务提供给下游，或修改、删除出湖作业。
- 必须分析：按材料分别选择功能分支和变更分支，两者可同时适用。功能分支按日、月、年等实际频率应用 `BIGDATA-01` 的日期、数据量和字符维度；事件状态覆盖文件正常、未到、晚到和重复，文件契约覆盖 bin/chk 不一致、只有 bin、只有 chk 和无交易空文件。正常时核对导出内容、记录数、文件配对、传输登记和接收目录；异常时核对等待、中断、报警或经材料确认的跳过策略。修改/删除分支只核对带出脚本、前后依赖及依赖作业组，并动态验证保留链路。
- 最低覆盖：功能分支对实际支持的正常、空文件、事件状态和文件契约异常各至少一条，并至少覆盖一条完整“湖表 → 文件生成 → 文件传输 → 下游接收”链路；仅发生修改或删除且没有功能变化时，功能分支记为 `NOT_APPLICABLE`，最低覆盖为静态依赖清理和动态续跑。两个分支同时适用时分别满足最低覆盖。
- 排除条件：未使用 bin/chk 时按实际文件契约替换，不机械生成不存在的配对场景；空文件、等待、中断/跳过和重复文件策略不明确时记为 `MISSING_EVIDENCE`，不得同时生成冲突预期；删除-only 变更不触发功能分支。
- 来源定位：`出湖/功能验证/出湖功能验证`；`出湖作业的修改、删除验证`。

## 投产前回归

### BIGDATA-21 BDP/BDSP 投产前改造范围评估与核心链路回归

- 适用域：`BDP`、`BDSP`。
- 触发条件：大数据平台工作单元进入投产前验证，或材料要求对当期改造范围和未改动核心作业进行回归。
- 必须分析：先按实际 `domainScopes` 分支执行，不得用 BDP 结果代替 BDSP，或反向替代。BDP 分支与开发共同白盒核对改造范围，完成新增表和依赖的 SEAS 静态检查、当期改造联测、BDP 日终作业回归、回装环境流水线部署以及表/视图权限和功能验证。BDSP 分支与开发共同白盒核对改造范围，完成新增表、作业依赖、SEAS 和带出排程文件静态检查、当期改造内容的单作业组调度、外部系统触发的全流程调度、回装环境流水线部署以及权限和功能验证。遵循测试原则：当期改造在投产前完成一轮全流程；未改动的 BDP 日间核心作业、BDP 日终作业和 BDSP 核心作业组按发布范围回归，防止外应用依赖变化引发次生问题。
- 最低覆盖：每个实际命中的领域分别形成一份“评估范围 → 实际变更 → 静态检查 → 调度/联测 → 流水线 → 已覆盖案例/未覆盖理由”核对结果。BDP 至少覆盖当期联测、日终回归和流水线；BDSP 至少覆盖单作业组、外部触发全流程和流水线；未改动核心链路按材料确认的 BDP 日间、BDP 日终、BDSP 核心清单逐项回归。缺少对应清单、流水线或调度入口时记为 `MISSING_EVIDENCE`。
- 排除条件：当前工作单元不涉及发布或投产前验证时不适用；不得用单作业成功替代全流程回归，也不得自行猜测核心作业清单。
- 来源定位：`测试原则` 第 3、4 项；`投产前 checklist` 中 BDP/BDSP 改造范围评估、日终回归和全流程要求。
